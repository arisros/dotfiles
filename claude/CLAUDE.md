# Global Rules

These apply in every project on this machine. A project CLAUDE.md may override any of them. Where a project says nothing, these hold.

## Language

Always write in English: replies, commits, PR titles and bodies, comments, docs, Jira. I often write Indonesian or mix it with English. Do not mirror my language, answer in English anyway.

## Attribution

Never add Claude attribution anywhere. No `Co-Authored-By: Claude`, no `Generated with Claude Code`, no session link, no "generated by" footer, in commits, PRs, issues, comments, docs, or Jira. This is enforced by `attribution` in `~/.claude/settings.json`; never reintroduce it by hand or per repo.

## Commit messages

Conventional Commits: `type(scope): subject`.

- Types: feat, fix, refactor, perf, test, docs, build, ci, chore, revert.
- Subject: imperative, lowercase, no trailing period, 72 chars max.
- Body only when the "why" is not obvious from the subject. Bullets, never paragraphs.
- Ticket key in the scope or a `Refs:` footer when the work has one, unless I say to leave it out.
- No trailers other than `BREAKING CHANGE:` and `Refs:`.

## Pull requests

- Title: same Conventional Commit format as the commit.
- Open as draft unless I say otherwise.
- Description is minimal by default:
  - one line of what changed
  - one line of why, a ticket link is enough
  - a mermaid diagram when the change is a flow, a sequence between services, or a state transition
  - a `## Test` section only when a reviewer actually has something to run
- No boilerplate headings that would be empty or that restate the diff ("Summary", "Changes", "Impact", "Risk", "Notes").
- Never narrate the diff back as prose. The reviewer already sees it.

## Diagrams over prose

When explaining a flow, a picture beats paragraphs, and text based beats an attached image. In order of preference:

1. mermaid (`sequenceDiagram`, `stateDiagram-v2`, `flowchart`), renders in GitHub, Jira and any markdown viewer
2. a markdown table
3. an ASCII box drawing

Never attach or generate a rendered image when a mermaid block will do.

## Writing style

- Never use an em dash or en dash in anything I read or anything published. Use a comma, a colon, parentheses, or a new sentence.
- No filler openers, no marketing adjectives, no announcing what you are about to do.
- Use a table when listing more than three items with attributes (PRs, tickets, services, versions).

## Code comments

Strict minimum. Zero comments is the default, not the exception.

- Delete comments that restate the code, narrate a change, mark sections, or talk to me ("added this", "as requested", "per review").
- Keep only: a non obvious why, a workaround with the cause it works around, a spec or ticket reference, and public API doc comments the project's own conventions already require.
- Never explain a diff in a comment. That belongs in the commit message.
- Remove stale and commented out code you pass over while editing a file.
- If a comment is only needed because the code is unclear, fix the code instead.
